## 4. WU4A scheduled integration

- Added `Generate WU4A team opportunity` step to `nfl-yardage-projections.yml`, positioned immediately before `Generate current-week yardage projections`, using the already-resolved `${{ steps.current-week.outputs.season/week }}` outputs — the same week-resolution step every other generator in this workflow already depends on, so no new "which week" logic was introduced.
- **No `continue-on-error`.** A generation failure (e.g. `generate-nfl-team-opportunity.ts`'s own fail-closed `throw` when `public/data/nfl/{season}/games.json` is missing/empty) stops the job before the projections step is ever reached — this is the entire mechanism that guarantees freshness (see Part 5/12).
- QA line already emitted by the generator (`teamRows=${artifact.qa.teamRowsEmitted}`, `bothTeamsPerGame`, `coherenceViolations`) reports whether a full slate produced 2 rows per game; I did not add a hard assertion on "32 teams / 16 games" because bye weeks and short/holiday slates are legitimate non-16-game weeks — the existing `bothTeamsPresentForEveryGame`/`coherenceViolations` QA fields already catch a *structurally* incomplete slate (a game missing one of its two team rows), which is the actual failure mode worth failing on. Hard-coding "16 games" would itself be a fail-closed bug during a real bye week.
- **Legitimate fallback path, and exactly when it is allowed:** none, at the workflow level, for WU4A generation itself — it is not fail-closed *optional*, it is fail-closed *required*. The only "fallback" in this system is WU4B receiving degrading to v1 when WU4A's artifact has no rows for the current week (see Part 5) — that is a downstream consumer's graceful degradation, not a silent fallback inside WU4A's own generation step.
- Public artifact (`public/data/nfl/{season}/team-opportunity.json`) added to the commit step's live-artifact `git add` list, alongside the existing `matchup-market.json`/`yardage-projections.json`.

## 7. Team-opportunity outcome resolution

- **Field-semantics audit (required before implementing, per the spec):** traced `teamOpportunityFeatures.ts`'s target derivation (`passAttempts: actual.passPlays`, `rushAttempts: actual.rushPlays`) back to `scripts/lib/nfl-epa-core.mjs`'s documented `classifyPlay` convention: sacks and QB scrambles are counted as **pass** plays (a true "dropback" definition), not as official box-score "attempts" (which exclude sacks/scrambles). So WU4A's `projected_pass_attempts`/`projected_rush_attempts` fields are — and always were — dropback/designed-rush counts under a legacy name, not what "pass attempts" means in a box score.
- **Resolution taken (documented, not silently papered over):** did **not** rename WU4A's own projection fields — that touches shipped WU4A code/tests and reads as a model-math-adjacent change, out of scope for an operational work unit under the model-scope lockout. Instead:
  - The new outcome `actual`/`derived` types use honest names: `dropbacks`, `designed_rush_attempts` (not `pass_attempts`/`rush_attempts`).
  - `dropbacks_error` compares `projection.projected_pass_attempts` (the actual trained target) against `actual.dropbacks` — the correct like-for-like comparison, sourced from the identical `play-volume-team-game` cache WU4A trains against.
  - A **separate, optional, diagnostic** `actual.pass_attempts` field sums official player-week passing attempts for the team when available (`actualPassAttemptsForTeam` in `nfl-prediction-outcome-resolver.ts`) — never required for resolution, always null when player stats are unavailable, so the two counts stay distinguishable for anyone doing further research.
  - Documented at length in `docs/modeling/PREDICTION_ARCHIVE_SCHEMA.md` (new "Naming note" subsection) and `docs/modeling/EVALUATION_DATASET_SCHEMA.md`, with an explicit recommendation that a future model-touching work unit rename the WU4A projection fields via a version-safe migration.
- Implementation: added a `prediction_type === "team_opportunity"` branch to `resolvePredictionOutcome` (`scripts/lib/nfl-prediction-outcome-resolver.ts`), inserted right after the shared game/result-finality checks (reused, not duplicated) and before the `spread` branch. It:
  - Requires only `games` + `results` + the new `teamPlayVolume` source (loaded from `data/nfl/nflverse/play-volume-team-game/play_volume_team_game_{season}.csv` via the existing `parsePlayVolumeCompactRow` parser) — **never** reads `playerStats`/`rosters` for its primary resolution path.
  - Returns a new `"pending_team_stats"` resolution status (distinct from `"pending_player_stats"`) when the play-volume cache exists but has no row yet for this exact game/team — so a dashboard can tell "waiting on team-level PBP aggregation" apart from "waiting on player box scores," which are different pipelines with different failure modes.
  - Returns `"source_missing"` when the cache was never loaded at all for the season.
  - Error convention: `projection - actual`, identical sign convention to every other family (verified by existing/new unit tests).

## 16. Explicit answers

- **Will a fresh scheduled runner generate WU4A before receiving v2?** Yes. `Generate WU4A team opportunity` runs immediately before `Generate current-week yardage projections` in `nfl-yardage-projections.yml`, with no `continue-on-error`, so a WU4A failure stops the job before the projections step (and therefore receiving v2) is ever reached. Verified by a workflow-ordering test.
- **Can receiving v2 ever silently use stale WU4A data?** Not from this workflow's own prior runs: because WU4A generation is fail-closed and runs immediately before the projections step in the *same job*, the `team-opportunity.json` on disk when the projections step reads it is always either (a) freshly written by this exact run, or (b) the job already stopped before reaching the projections step. The only remaining path to "not this run's data" is the pre-existing, disclosed WU4B behavior of falling back to v1 when the (fresh) artifact has no rows for the exact target week — that is a disclosed degrade-to-v1, not a silent stale-data consumption.
- **Can team_opportunity predictions now resolve?** Yes. A dedicated resolver branch grades them against the `play-volume-team-game` cache, independent of player-week stats, with a distinct `pending_team_stats` status for the one real gap (cache not yet refreshed for this game).
- **Can evaluations now measure WU4A accuracy?** Yes. `TeamOpportunityEvaluationRow` plus `teamOpportunityExtras` in the metrics module report plays/dropbacks/dropback-rate/designed-rush MAE and bias, with home/away, favorite/underdog, spread-bucket, total-bucket, and model-version cohorts, wired into the same scheduled workflow as resolution.

- **Is there any remaining P0 preventing Week 1 production?** No new P0 was found. The items in Part 15 are P1/P2 hardening and observability gaps, plus the standard caveat that no scheduled workflow change in this repo has been proven safe until its first real scheduled run is watched.
